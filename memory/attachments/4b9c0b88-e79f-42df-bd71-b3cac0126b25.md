An Activity Diagram with Swimlanes (formally known in UML as an **Activity Diagram with Partitions**) maps the flow of control, decisions, and data across different organizational roles, systems, or departments.

Adhering to standard design principles ensures models remain readable, technically unambiguous, and maintainable.

---

## 1. Partition & Swimlane Structure

Swimlanes establish architectural boundaries and operational ownership.

* **Partition Types:** Swimlanes should represent distinct **roles** (e.g., *Customer*, *Billing Specialist*), **systems/components** (e.g., *Frontend Client*, *Auth Service*, *Payment Gateway*), or **business domains**. Avoid mixing abstraction layers (e.g., do not place *Database* next to *Regional Sales Manager* unless modeling low-level technical interactions).
* **Orientation:** Use **vertical lanes** for sequential end-to-end user workflows or document lifecycles (top-to-bottom flow). Use **horizontal lanes** primarily for system integration or pipeline views where chronological progression reads naturally left-to-right.
* **Lane Count:** Limit diagrams to **3 to 6 lanes**. More than 6 lanes causes visual clutter, excessively long cross-lane connectors, and degraded readability. Group nested subsystems into a parent lane using multi-dimensional partitions if necessary.
* **External Entities:** Position external or third-party systems (e.g., *Stripe API*, *Identity Provider*) on the outermost lane (far right or far left) to minimize connector crossings.

## 2. Standard UML Notational Elements

| Element | UML Notation | Design Standard / Rule |
| --- | --- | --- |
| **Initial Node** | Solid black circle (`●`) | Exactly **one** initial node per major workflow. Always placed in the initiating lane. |
| **Activity / Action** | Rounded rectangle | Must use an **Active Verb + Noun** phrase (e.g., *Validate Token*, *Calculate Tax*). Keep it atomic. |
| **Control Flow** | Solid arrow (`───►`) | Indicates sequential progression. Must not represent data payload unless using object pins. |
| **Decision Node** | Diamond (`◇`) with 1 in, 2+ out | Outgoing edges **must** have mutually exclusive, complete guard conditions in square brackets `[Condition]`. |
| **Merge Node** | Diamond (`◇`) with 2+ in, 1 out | Merges alternate alternative branches from a previous decision. Never combine Decision and Merge into one diamond. |
| **Fork Node** | Solid black bar (1 in, 2+ out) | Splits a flow into concurrent/parallel paths. |
| **Join Node** | Solid black bar (2+ in, 1 out) | Synchronizes parallel paths. Execution halts until **all** incoming paths arrive. |
| **Object Node / Pin** | Standard rectangle | Represents state/data objects passed between actions. Connected via dashed or object flow arrows. |
| **Activity Final Node** | Bullseye circle (`◉`) | Terminates the entire activity and all concurrent threads immediately. |
| **Flow Final Node** | Circle with an "X" (`⊗`) | Terminates only that specific path without stopping parallel flows. |

## 3. Flow & Layout Best Practices

* **Directional Discipline:** Direct flow consistently in one primary direction (downward or left-to-right). Upward/backward arrows should **only** represent explicit loops or retries.
* **Line Crossings:** Route edges to eliminate or minimize line intersections. When intersections cannot be avoided, use a bridge/jump arc or reorder the swimlanes to make adjacent actors physically adjacent on the canvas.
* **Atomic Decisions:** Decision diamonds must be contained entirely within the lane responsible for the evaluation. Do not place a decision diamond across a swimlane border.
* **Explicit Merges and Joins:**
* Do not connect multiple arrows directly into an Action node to represent alternatives; route them through a **Merge Node** first.
* Never use a Join Node to combine mutually exclusive paths from a Decision—this results in a structural deadlock, as the Join will wait forever for the path not taken.


* **Loop Boundaries:** Clearly label loop termination conditions. Every loop must have an explicit exit guard condition leading forward.

---

## 4. Semantic Rules & Clean Modeling

* **Naming Conventions:**
* **Actions:** Present tense verb phrases (`Submit Claim`, not `Claim Submitting` or `Claim`).
* **Guards:** Boolean assertions (`[Payment Approved]`, `[Payment Declined]`, `[Invalid Credentials]`).
* **Objects:** Noun with state (`Order [Created]`, `Invoice [Paid]`).


* **Level of Abstraction:** Keep all actions within the same diagram at a uniform level of granularity. If an action hides substantial complexity (e.g., an entire checkout pipeline), mark it as a **CallBehavior Action** (using a rake icon `⑂` in the lower right) and break it out into a separate sub-activity diagram.
* **Idempotency & Rollback:** When modeling transaction rollbacks, compensation actions must trace cleanly back across lanes to show how state is cleaned up in external systems or databases.

## 5. Quick Review Checklist

Before publishing or committing an activity diagram, verify:

1. [ ] Is there exactly one primary start node in the initiating swimlane?
2. [ ] Does every Decision diamond have labeled, mutually exclusive guards on every outgoing branch?
3. [ ] Are parallel paths (Fork) synchronized with a Join, rather than dangling?
4. [ ] Are all action labels phrased as *Verb + Noun*?
5. [ ] Is the number of swimlanes kept to 6 or fewer?
6. [ ] Are backward flows strictly limited to retry/loop mechanisms?
